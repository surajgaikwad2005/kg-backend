Purpose of this document:
The full specification is long and detailed. This summary covers only three
questions, in order, so the topic can be presented and decided in a short
meeting:

    1. What exactly is the problem?
    2. How do we solve it?
    3. What APIs must be built, how many, and how do they work?


===============================================================================
SECTION 1 - THE PROBLEM
===============================================================================

1.1 ONE-LINE STATEMENT
-------------------------------------------------------------------------------
Files reach the backend correctly. The lifecycle around those files does not
exist on the backend at all. It exists only inside the user's web browser.


1.2 WHAT THIS MEANS IN PRACTICE
-------------------------------------------------------------------------------
The following information is currently stored in browser local storage, not
in any database:

    - Which data sources have been configured
    - Which sources have been processed
    - Which sources have been validated
    - Which sources have been committed
    - When each of those happened
    - Which job IDs and batch IDs belong to which source
    - Which files were uploaded under which document type

This is held across 12 separate browser storage keys.

Additionally, processing progress shown to the user (the 0% to 100% bar) is
not real. It is generated in the browser using a random number, because the
backend does not return any progress value.


1.3 PRIMARY TECHNICAL CAUSE
-------------------------------------------------------------------------------
The pipeline status endpoint currently returns:

    GET /pipeline/jobs/{id}
    -> pipeline_job_id, stage, plant_code_id, upload_batch_id,
       status, output_tables, record_counts, total_records

There is no progress field of any kind in this response.

Because the backend reports no progress, the frontend fabricates it. This is
the single root cause of the most visible issue in the product.


1.4 BUSINESS IMPACT
-------------------------------------------------------------------------------
    a) DATA LOSS
       If a user clears browser data, the entire configuration history for
       that plant is lost. The backend cannot reconstruct it.

    b) NO SHARED TRUTH BETWEEN USERS
       Two administrators configuring the same plant see two different
       states. There is no single version of the truth.

    c) WORK IS LOST ON REFRESH
       Refreshing the page during processing orphans the running job. The
       job continues on the server, but the interface can no longer find it.

    d) PROGRESS IS NOT TRUSTWORTHY
       A user cannot tell the difference between "slow but healthy" and
       "stuck and failed". Support cannot diagnose either.

    e) NO AUDIT TRAIL
       We cannot answer: who committed this data, when, from which files,
       and using which settings. This is a compliance exposure.

    f) NO RESUME OR RETRY
       The system does not know what already succeeded, so failed work
       cannot be resumed. It must be restarted from the beginning.

    g) FAILURES CAN BE REPORTED AS SUCCESS
       In the P&ID ingestion flow, the progress indicator completes and
       reports success even when the underlying upload has failed.


===============================================================================
SECTION 2 - THE SOLUTION
===============================================================================

2.1 GOVERNING PRINCIPLE
-------------------------------------------------------------------------------
Every fact displayed in the interface must be readable from the backend,
identified by plant code alone.

The backend becomes the owner of the entire lifecycle. The frontend becomes
a display layer only. It uploads files, sends user intent, and displays
whatever the backend reports. It stores nothing that must survive a refresh.


2.2 WHAT THE BACKEND MUST STORE
-------------------------------------------------------------------------------
Six persistent record types:

    BATCH      One upload or cloud sync action. Groups files that arrived
               together.

    FILE       One physical file. Carries its identity, type, subtype,
               size, checksum, extracted metadata, and processing status.

    RUN        One execution of a processing pipeline over one or more
               batches.

    STAGE      One named step inside a run (validate, preprocess, OCR,
               extract, compare, load), each with its own real progress.

    COMMIT     An immutable record of data written to the database, with
               actor, timestamp, and row counts.

    EVENT      An append-only log line for each run, for support and audit.


2.3 REAL PROGRESS - HOW IT IS CALCULATED
-------------------------------------------------------------------------------
    - Each stage declares a weight.
    - Run progress = sum(weight x stage progress) / sum(weight).
    - Stage progress comes from countable work: files done of files total,
      pages done of pages total, rows loaded of rows total.
    - Progress is calculated by the server, never by the browser.
    - Progress only increases. It never moves backwards.
    - Progress is saved, so it survives a server restart.
    - 100% is reported only when the run has actually finished.
    - Where nothing is countable, the backend states this explicitly and
      the interface shows an indeterminate indicator. An honest
      indeterminate indicator is better than a false percentage.


2.4 ACCEPTANCE CRITERIA
-------------------------------------------------------------------------------
The work is complete only when all three of the following pass, for every
connector and every step:

    TEST 1 - REFRESH TEST
    Refresh the page during processing. The interface returns to the same
    step with the same real progress. Nothing is lost or restarted.

    TEST 2 - SECOND DEVICE TEST
    Open the same plant on a different machine or user account. The same
    state is shown, including a job that is currently running.

    TEST 3 - CLOSED TAB TEST
    Close the browser tab entirely during processing. The job continues on
    the server and can be found and resumed later.

SECTION 3 - THE APIs
===============================================================================

3.1 HOW MANY APIs - THE DECISION
-------------------------------------------------------------------------------
Two approaches were rejected:

    REJECTED: One single API endpoint for everything.
    Reason: The request body becomes a combination of four unrelated
    formats, which cannot be validated or documented. All operations share
    one address, so logging, monitoring, access control and timeout limits
    cannot distinguish a 2 GB file upload from a status check.

    REJECTED: A separate API for every step of every connector.
    Reason: 4 connectors x approximately 13 steps = more than 50 endpoints,
    of which around 80% would be duplicates of each other. Four copies of
    upload, four copies of status polling, four copies of commit.

    APPROVED: One generic set of endpoints, with the connector name as a
    parameter.

Total: approximately 29 endpoints.


3.2 THE THREE TIERS
-------------------------------------------------------------------------------

    TIER 1 - GENERIC CORE                                    16 endpoints
    -------------------------------------------------------------------
    Identical endpoints for all four connectors. The connector name is a
    parameter in the path.
    Delivers 100% of the lifecycle for all four connectors.

    TIER 2 - CATALOGS AND CONFIGURATION                       5 endpoints
    -------------------------------------------------------------------
    Reference data that differs by connector: the document type tree, the
    SAP table list, the available AI model list, and the last-used
    processing settings.

    TIER 3 - CONNECTOR SPECIFIC                               8 endpoints
    -------------------------------------------------------------------
    Only where an operation has no equivalent in the other connectors:
    P&ID page editing, crop area preview, template matching, connection
    validation, and Time Series data quality analysis.

                                                     TOTAL: ~29 endpoints


3.3 WHY THIS WORKS - THE COMMON PATTERN
-------------------------------------------------------------------------------
All four connectors perform the same six operations. Only the internal work
inside a processing run differs.

    upload files -> list files -> start run -> watch progress ->
    review data -> commit

           |            |            |             |
           +------------+------------+-------------+-----------+
           identical for P&ID, Documents, Time Series and SAP


3.4 THIS IS AN EXISTING PATTERN, NOT A NEW ONE
-------------------------------------------------------------------------------
The current production backend already uses this approach successfully:

    POST /pipeline/run     accepts a stage parameter:
                           sap | docs | ts | pnid | full
                           One endpoint. All connectors. Already verified
                           working against the live backend.

    Connector file upload and job polling are also already parameterised
    by connector name in the existing service layer.

This proposal extends a pattern that is already proven in this system. It
does not introduce a new architectural concept.


3.5 RULE FOR THE ENGINEERING TEAM
-------------------------------------------------------------------------------
Create a connector-specific endpoint ONLY when the operation has no meaning
for the other three connectors.

    "Delete page 5 of a PDF"
        -> Meaningful only for P&ID
        -> Connector specific endpoint. Correct.

    "Which files have been processed?"
        -> Meaningful for all four connectors
        -> ONE endpoint with connector as a parameter. Correct.
        -> Four separate copies. Incorrect.


3.6 HOW A REQUEST WORKS - END TO END
-------------------------------------------------------------------------------
    STEP 1  User uploads files.
            Backend creates a batch, stores each file, extracts its
            metadata (page count, sheet names, row counts), validates it,
            and returns a batch ID and a file record for every file.

    STEP 2  User starts processing.
            Backend creates a run, locks the connector so a second run
            cannot start, and returns a run ID plus the list of planned
            stages.

    STEP 3  Interface watches progress.
            Preferred: a live event stream.
            Required fallback: polling every 2 to 3 seconds.
            Both must be implemented, because network and gateway
            conditions vary across deployments.

    STEP 4  User reviews extracted data.
            Backend returns staged rows with stable row identifiers,
            column definitions, and validation issues. Edits are saved to
            the backend before commit, not held in the browser.

    STEP 5  User commits.
            Backend writes to the database and returns a commit ID, per
            table row counts, and any rejected rows. The operation is
            repeat-safe: a duplicate submission does not write twice.


3.7 RESPONSE FORMAT
-------------------------------------------------------------------------------
All endpoints use the response wrapper already in use in the current system:

    {
      "success": true,
      "message": "...",
      "data":    { ... }
    }

Two existing endpoints do not follow this format and must be corrected for
consistency. They are identified in the full specification.


===============================================================================
SECTION 4 - DELIVERY PLAN
===============================================================================

    PHASE 1 - STATE
    Store batches, files and connector state. Provide read endpoints.
    Result: browser storage is removed. Refresh Test passes for state.

    PHASE 2 - REAL PROGRESS
    Add runs, stages and progress calculation.
    Result: all fabricated progress is removed. Refresh Test passes for
    running jobs.

    PHASE 3 - STREAMING AND CONTROL
    Live event stream, cancel, retry, duplicate-request protection.

    PHASE 4 - FILE LEVEL TRACKING
    Per-file processed status, duplicate detection by checksum, cloud
    incremental sync.

    PHASE 5 - SETTINGS AND CATALOGS
    Persist processing settings; move the document type and SAP table
    catalogs to the backend.

    PHASE 6 - AUDIT AND GOVERNANCE
    Commit history, access control per action, audited reset.

    NOTE: Phases 1 and 2 together resolve the majority of the visible
    problem and are the recommended first milestone.


===============================================================================
SECTION 5 - DECISIONS REQUIRED BEFORE DEVELOPMENT
===============================================================================

The following must be agreed before implementation begins. Each one affects
work in more than one team.

    1. TWO PARALLEL P&ID PIPELINES
       Two separate P&ID implementations currently exist on two different
       backends, with no shared state. One must become the system of
       record, or the two must be merged. This blocks all P&ID work.

    2. LIVE EVENT STREAM SUPPORT
       Confirm whether a live event stream can pass through the existing
       gateway. If not, the polling interval and payload size must be
       agreed instead.

    3. COORDINATE SYSTEM FOR THE P&ID SELECTION AREA
       The processing area selected by the user must be defined in one
       stated coordinate system and used consistently.

    4. PAGE NUMBERING
       Page numbers must be defined as starting from 0 or from 1, once,
       and applied to every endpoint.

    5. PARTIAL SUCCESS POLICY
       If 8 of 10 files process successfully, may the user review and
       commit those 8, or must all 10 succeed first?

    6. DELETION AFTER COMMIT
       Define whether committed source files may be deleted, and the exact
       scope of the "Reset Pipeline" operation.

    7. DATA RETENTION
       Define how long uploaded files, generated outputs, and run history
       are retained.


===============================================================================
SECTION 6 - SUMMARY
===============================================================================

    PROBLEM     The backend stores files but not the lifecycle around
                them. Configuration state lives in the browser and
                progress is fabricated, because the status endpoint
                returns no progress value.

    SOLUTION    The backend takes ownership of batches, files, runs,
                stages and commits, and reports real calculated progress.
                The frontend becomes a display layer only.

    APIs        Approximately 29 endpoints. 16 are generic and serve all
                four connectors through a connector parameter. This
                extends a pattern already working in the current system.

    FIRST STEP  Phases 1 and 2 remove browser-stored state and fabricated
                progress. This is the recommended first milestone.
